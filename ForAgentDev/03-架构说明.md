# 03 · 架构说明

> 最后更新：2026-08-16 · 适用：multica-fanout

## 1. 系统分层

```
┌─────────────────────────────────────────────┐
│  用户 / 管理平台（未来：前端面板）                │
│  批量派发 UI · 实时看板 · 结果对比视图            │
└───────────────────┬─────────────────────────┘
                    │ 调用（CLI / 后续可加 API）
┌───────────────────▼─────────────────────────┐
│  multica-fanout（本仓库 CLI 编排层）            │
│  bin/fanout.js    ← 命令入口（commander）      │
│  src/dispatch.js  ← 业务：dispatch/status/aggregate
│  src/templates.js ← 子任务描述模板（防冲突）     │
│  src/multica.js   ← multica 命令封装（唯一IO点） │
└───────────────────┬─────────────────────────┘
                    │ spawn + JSON（MULTICA_BIN 可注入）
┌───────────────────▼─────────────────────────┐
│  Multica（外部底座）                           │
│  Issue/Task 状态机 · Agent 调度 · Daemon 执行  │
└─────────────────────────────────────────────┘
```

## 2. 核心数据流

### 2.1 派发（dispatch）

```
1. 校验 multica 可用（version）
2. multica agent list → 解析工作区智能体
3. 校验并解析 --agents（精确 > 前缀 > 包含，歧义报错）
4. 创建父 Issue（聚合点，不 assign）
5. 循环 i ∈ [1..N]：
   生成子任务描述（模板：背景 + 视角 i + 产出规范）
   multica issue create --parent <父> --assignee <agent> --status todo
6. 输出派发报告（父/子 ID 映射 + agent 映射）
```

### 2.2 进度（status）

```
multica issue get <父>            → 父状态
multica issue children <父>        → 子列表（按 stage 分组）
→ 输出 { key, title, assignee, status }
```

### 2.3 聚合（aggregate）

```
1. 轮询 children 直到全部达到终态（done/in_review/cancelled）
2. 每个子 Issue：multica issue comment list（取最近内容较长的评论作为产出）
3. 产出落盘：<outDir>/<slug>-<agentKey>.md
4. 生成汇总报告（buildAggregateSummary）回写父 Issue 评论
```

## 3. 关键设计决策

| 决策 | 理由 |
| --- | --- |
| 1 父 + N 子 Issue 并行 | 绕过 Multica「1:1 分配」限制，官方认可；父子同批 todo 即并行 |
| 子任务描述注入隔离目录 + 统一文件名 | 多 Agent 并行不互相覆盖文件 |
| 产出走 Issue 评论聚合 | 审计友好、跨 Agent 解耦、人类可介入（同 Multica 设计哲学） |
| `MULTICA_BIN` 可注入 | 测试 mock 化；未来可替换为 API 代理 |
| 同步 spawn + JSON | CLI 场景简单可靠，避免异步状态机复杂度 |
| 进度日志走 stderr | `--json` 模式 stdout 干净可解析 |

## 4. 模块职责边界

| 模块 | 职责 | 禁止 |
| --- | --- | --- |
| `src/config.js` | 连接配置加载（配置文件/环境变量/CLI 三级优先级）、全局 flag 拼装 | 业务判断 |
| `src/multica.js` | 唯一直接调用 multica 命令的模块，注入全局连接 flag | 业务判断 |
| `src/dispatch.js` | 编排逻辑、解析、轮询、聚合 | 直接 spawn |
| `src/templates.js` | 纯函数生成 markdown | 副作用 |
| `bin/fanout.js` | 参数解析、IO 呈现 | 业务逻辑 |

## 4.1 连接配置数据流

```
命令行 --profile/--workspace-id/--server-url/--config
      ↓ (高)
环境变量 MULTICA_PROFILE / MULTICA_WORKSPACE_ID / MULTICA_SERVER_URL / MULTICA_BIN
      ↓ (中)
配置文件 ./multica.config.json 或 ~/.multica-fanout.json
      ↓ (低)
configureRuntime() 合并 → runtime 单例
      ↓
globalFlags() → 每条 multica 命令前置注入：
  multica [--profile p] [--workspace-id ws] [--server-url url] <command> ...
```

- token 不进入该链路，由 `multica login` 独立管理（配置只含地址/身份指向，不含凭证）；
- 测试用 `MULTICA_BIN` + fake/spy 验证注入（见 `test/fanout.test.mjs`「config」组）。

## 4.2 真实 Multica CLI 返回结构约定（重要）

对接真实服务器（v0.4.13）时发现的差异，**开发时必须遵守**：

| 项 | 真实 CLI | 注意 |
| --- | --- | --- |
| issue 编号字段 | `identifier`（如 `VC-234`），**没有 `key`** | 统一用 `normalizeIssue()` 映射为 `key`；工作区前缀是 `VC` 不是 `MUL` |
| `issue children` | 必须加 `--output json`，返回 `{ stages: [], total, unstaged: [...] }` | 默认是表格！`flattenChildren()` 已兼容该结构 |
| `issue list` | 返回 `{ has_more, issues: [...] }` | `asArray()` 解包 `issues` |
| children 的负责人 | 只有 `assignee_id` / `assignee_type`，无名字 | `status()` 内部用 `agentList()` 做 id→name 映射 |
| `issue create/get/assign/status` | 默认 JSON，无需 `--output json` | — |
| 分配即执行 | 非 backlog 的 issue 分配给 agent 会立即入队执行 | 调试时避免真实派发；用 fake 或创建后立刻 cancelled |

`fake-multica.mjs` 已按上述真实结构模拟（`identifier` + `{stages,total,unstaged}`），测试覆盖真实路径。

## 5. 多视角并行模板（防冲突核心）

每个子任务描述强制包含：
1. 视角编号（index）与视角说明
2. **工作目录隔离**：产出只写 `output/<agent-key>/`
3. **统一文件名**：`view-<n>-<agent-key>.md`
4. 统一内容结构：结论摘要 / 论据与理由 / 建议 / 风险
5. 交付标准：产出回贴评论 + 状态置 `in_review`

## 6. 扩展点（未来）

- **API 化**：在 multica.js 之上加 HTTP 服务层（Node http / Fastify），供前端面板调用；
- **WebSocket 实时推送**：订阅 Multica /ws 事件，前端看板实时刷新；
- **对比视图**：聚合时对多份产出做 diff/并排高亮；
- **多项目**：仓库根新增项目目录，遵循本架构的分层约定（每项目自带 multica.js 等价物）。
