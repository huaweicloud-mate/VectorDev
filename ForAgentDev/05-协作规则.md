# 05 · 协作规则

> 最后更新：2026-08-16 · 适用：所有进入 VectorDev 的开发者（人类 + Agent）

## 1. 总原则

- **Issue 是协作的唯一事实源**：任务背景、讨论、决策、产出都在对应 Issue（Multica）中；
- **一次一个职责**：一个任务一个 Issue，一个 PR 只解决一个 Issue；
- **先确认后动手**：超出任务范围的工作，先在 Issue 评论确认再实施。

## 2. 任务流转

```
backlog（待定）→ todo（已明确）→ in_progress（进行中）→ in_review（待审查）→ done（完成）
                                                              ↘ blocked / cancelled
```

- Agent 领取后：`todo → in_progress`（开工即改状态）；
- 产出提交后：`in_progress → in_review`；
- `done` 通常由人类确认，或由集成（如 PR 合并）置位。

## 3. 分支与提交

```bash
# 分支命名
feat/<issue-key>-<简述>      # 如 feat/MUL-42-batch-dispatch
fix/<issue-key>-<简述>
docs/<简述>

# 提交信息见 04-代码规范 §6（Conventional Commits）
```

## 4. PR 规范

- PR 标题：`<type>(<scope>): <简述> [MUL-xxx]`（关联 Issue）；
- PR 描述：背景 / 改动 / 测试结果 / 文档更新清单；
- 合并前检查：`npm test` 绿、文档同步、无敏感信息；
- 小步提交：PR 保持可审查规模（< 400 行变更）。

## 5. 多 Agent 并行隔离（重点）

多个 Agent 同时在本仓库工作时：

| 冲突源 | 约定 |
| --- | --- |
| 文件写入 | 每个 Agent 产出写自己的隔离路径 `output/<agent-key>/`（Issue 描述指定） |
| 共享文档 | 修改 `AGENTS.md` / `ForAgentDev/*` 前，先检查是否有未合并的相关 PR |
| 同一文件 | 避免多人改同一文件；必要时用 Issue 评论先声明「我在改 X」 |
| 分支 | 每个任务独立分支，互不共用；冲突交给 Git 合并 + 人类审查 |
| 环境变量 | 本地 mock 状态文件（`FAKE_STATE_FILE`）不要提交，各自用独立文件 |

### 并行派发专用流程（multica-fanout）

```
1. dispatch：1 父 Issue + N 子 Issue（每个 Agent 一个，视角独立）
2. 各 Agent 独立执行，产出回贴自己的子 Issue 评论
3. aggregate：N 份产出落盘 + 汇总对比回写父 Issue
```

## 6. 跨 Agent 沟通

- 用 Issue 评论 + @mention，**不要**跨 Agent 直接读对方记忆/上下文；
- 需要协作时：`@agent-b` 提出具体问题，对方被触发后回答并回贴；
- 所有交互留痕在 Issue，人类随时可介入修正方向。

## 7. 敏感信息红线

- 永不提交：`.env`、token、密钥、PAT（见 `.gitignore`）；
- Multica CLI 配置含令牌（`~/.multica/config.json`），不进仓库；
- 讨论成本/价格/未确认承诺：只存在于内部，不写入客户可见文档。

## 8. 审查者清单（合并前）

- [ ] 测试通过（`npm test`）
- [ ] 变更在 Issue 声明范围内
- [ ] 文档已同步（行为/接口/命令变更时）
- [ ] 无敏感信息、无未授权内容
- [ ] 提交信息符合规范，关联 Issue
